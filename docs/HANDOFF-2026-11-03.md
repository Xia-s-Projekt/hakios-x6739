## Fixes that reached the home screen

### `/private/var` capacity

LaunchServices originally filled ramfs, returned `ENOSPC`, and crashed `lsd`. The first quota experiment was wrong: it wrote `rm_max_pages = 0x3000`, which is only 48 MiB with the kernel's 4 KiB pages. The corrected binary computes:

```
(max_mem * 3 / 8) / runtime_page_size
```

With XNU's 512 MiB window, `/private/var` is 192 MiB. Device proof:

- `logs/xnu-c4-300-sb-sqlite.log:2120-2122`: the broken experiment reports 12,288 blocks × 4,096 bytes and zero free blocks; SpringBoard exits on `SQLITE_FULL` while committing `/var/mobile/Library/DuetExpertCenter/_ATXInfoSuggestionStore.db`.
- `logs/xnu-c4-300-ramfs192-corrected.log:2293`: corrected mount reports `201326592 bytes` capacity.
- same run reaches the home screen; timed panel sample 6 has 1,643 non-black pixels and 305 colors.

The promoted kernel differs from `logs/mach.before-ramfs-capacity` at the ramfs calculation only by:

- `0x583564`: `lsr x8, x8, #2` → `lsr x8, x8, #3`;
- `0x583574`: `sxtw x9, w9` → `add x8, x8, x8, lsl #1`;
- existing `udiv x8, x8, x9` then divides by runtime page size.

The common-tree source has an uncommitted `ramfs_mb` boot-arg experiment at:

`../refs/hakios-xnu-kernel/xnu-src/xnu-8796.121.2/bsd/miscfs/ramfs/ramfs.c`

That source is not the exact binary implementation above and remains common-tree work.

### FT3681 touch

The kernel driver initialized `command = FTS_REG_REPORT`, then changed it to `0xa6` while reading firmware version and never restored it. Polling therefore read the firmware register every 5 ms and emitted a constant fake contact.

Fix: reset `command = FTS_REG_REPORT` immediately before the polling loop in:

- `kernel/bsd/dev/hakios.ft3681.c`;
- common-tree copies under `../refs/hakios-xnu-kernel/drivers/input/` and `xnu-src/.../bsd/dev/` (uncommitted there).

The tested kernel has the equivalent guarded binary change at file offset `0x4dbbd0`: `mov w8, #0xa6` → `mov w8, #1`.

Proof in `logs/xnu-c4-300-touch-smalljobs.log`:

- lines 736-737: 2,400 untouched polls, all idle, zero points;
- lines 2273-2275: real FT3681 press/contact reports appear;
- line 2280 onward: reports and decoded points increase only after interaction;
- user confirmed taps and swipes control the UI.

Touch is working. Do not infer anything from unattended runs after this one.

## Graphics: exact current limitation

The current graphics path is CPU software rendering:

- `tools/build-graphics.sh:48` builds Mesa with `DRIVERS=softpipe`;
- `userland/src/gl_osmesa.c` uses OSMesa;
- `MiniIOMobileFramebuffer.cpp` copies IOSurface pixels into LK's framebuffer on CPU;
- the Mali-G77 receives no rendering work.

The user confirmed home screen, blur in recents, and flicker/low FPS. Logs prove:

- framebuffer copy takes about 2-4 ms per submitted frame;
- every frame reports zero time waiting for the GPU;
- default `fb_filter=2` redraws almost every submitted frame bilinear after 40 ms, which is a likely source of visible flicker at low FPS;
- normal reduced-job run peaks at 6 FPS (`logs/xnu-c4-300-touch-smalljobs.log:2278`);
- `fbscale=2` still peaks at 10 FPS and triggers UIKit's red fallback status bar `rdar:45025538`; cache string says no status-bar visual provider matches that screen width/scale/idiom/corner radius. Do not use `fbscale=2` permanently;
- normal scale with `fb_filter=0 fb_ca_hz=120` sustains about 10 FPS, eliminates all filtered redraws, and keeps framebuffer-copy time near 3.3 ms (`logs/xnu-c4-300-filter0-ca120.log:2253-2335`).

The 10 FPS cap is upstream of framebuffer copy. **Hypothesis:** display-link pacing and/or softpipe rendering time. A profiling run used `touch_lat=1 glframes=1 glslow=10000`, but the selected 430,000-byte XNU log window still missed the `hakios-gl` lines. Do not claim a measured GL bottleneck from that run.

Older retained evidence does show softpipe frame costs:

- `logs/xnu-c4-400-window.log:1653`: first frame 656,751 µs, including initial IOSurface uploads;
- `logs/xnu-last.log:1151,1245,1282,1296,1303`: later frames range 12,951-85,228 µs.

Real acceleration is substantial work, not a boot argument. `docs/metal-plan.md` describes an Adreno-oriented path from another device; this phone has Mali-G77/Valhall. X6739 placeholders and evidence are in `kernel/README.md`, `docs/port-plan.md`, and `docs/mt6893-facts.md`. Start from the phone's vendor modules and device-tree addresses; do not carry MT6768/G52 numbers over.
