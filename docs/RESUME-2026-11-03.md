# Where the port stands, for whoever picks it up

Written 2026-11-03, mid-session, and updated the same evening after patch 7 was made and run.
Everything below is from a run on the phone or from a file that was read; nothing is a guess.
Where something is a hypothesis it says so.

## The short version

The kernel that was being flashed was the tree's prebuilt from 1 November, patched byte-wise
for this phone. This session replaced it with the **source-built** kernel, and that exposed
two things:

1. The source tree's UFS host controller was at the **reference board's** address
   (`0x1d84000`), not this phone's (`0x11270000`). Fixed. With that fixed the kernel boots
   and finds the storage.
2. The source tree is missing **9 of the 13 byte-level patches** the prebuilt carried. The
   byte patcher is the list of what this phone needs; the source tree has only 2 of them
   (`ufs-lun`, `code-signing-16k`). **That is the main open work.**

**Patch 7 is now done too** (three of thirteen), and the storage blocker with it: see "The
storage reads now" below. The run reached `launchd.ios`, `backboardd` and `SpringBoard` on the
iOS volume, which is the furthest this phone has ever gone.

The phone now reaches the iOS home screen and touch works. This document records the earlier
storage/source-kernel work; `docs/HANDOFF-2026-11-03.md` has the current state, proof and next work.

## The UFS address (fixed)

`bsd/dev/hakios.ufshc.c:76` in the source tree said:

```c
#define UFSHC_PHYS          0x1d84000ULL   /* ufshc@1d84000, "ufs_mem", in the phone's Android device tree */
```

The comment is false. `0x1d84000` is the reference board's Qualcomm controller and it does
not appear anywhere in this phone's device tree. The phone's own tree (`refs/fdt-x6739.dtb`)
says:

```
/soc/ufshci@11270000 reg = 0x11270000 size 0x2300
    compatible = mediatek,mt8183-ufshci
```

`strings refs/fdt-x6739.dtb | grep -c 1d84000` → 0; `grep -c 11270000` → 2. The loader's
own `UFSHCI_BASE` in `mtkloader/mt6893.h:182` is `0x11270000`. Changed to `0x11270000`.
Effect, from the run log:

```
ufs: native: controller at 11270000: CAP 3587071f (32 slots, 64-bit yes), VER 00000200, ...
```

## The nine missing patches — this is the main work

what the source tree still lacks. Only two have been converted to source:

* `docs/kernel-source-patches/ufs-lun.patch` — the LUN mask and the LUN search.
* `docs/kernel-source-patches/code-signing-16k.patch` — `cs_validate_hash()` stubbed,

## The storage still dies at 48 s

> **Superseded in part, 2026-11-03 later the same day.** Patch 7 was made in the source and the
> run proves the native driver now comes up (`ufs: native: usable: a list of 32 slots at
> 80210000`). What blocks it now is `ufs_native_map`, which asks the *loader* to read block 1
> first -- and our loader has no service loop, so that read times out. See "After patch 7"
> below. The chain below is kept as it was written, because it is how the refusal was found.

From the 300 s run (`~/.hermes/cache/scratch/fix1.log`):

```
[ 48.125614]: ufs: no answer from the loader to request 1 in 20 s: the storage is off from now on
[ 48.138991]: mount /dev/ufs_xnusys: Input/output error
[FAIL] mount the iOS volume read only
```

Compare the **old** prebuilt kernel (`~/.hermes/cache/scratch/glq.log`), which did mount it:

```
apfs: volume 0 "System" of container 0 (at 0 MB): 45044 files, 16547 directories, 601698 blocks of 4096 used
[ ok ] mount the iOS volume read only
```

So the old kernel read the storage; the new one does not.

The chain, from `bsd/dev/hakios.ufshc.c` and `bsd/dev/hakios.ufs.c`:

1. `hakios.ufshc.c` has two ways to read: drive the controller itself (`ufs_native`), or ask
   the loader, one request at a time (`hakios.ufs.c`).
2. The new kernel's own driver **refuses** to run:

   ```
   ufs: native: not used: UEFI's command descriptor is not where it was; the storage is read through the loader
   ```

   That string comes from `_hc_uefi_slot0()` in `hakios.ufshc.c`:

   ```c
   uint64_t ucd = (uint64_t)hc_uefi_list[5] << 32 | hc_uefi_list[4];
   if (ucd < hc_uefi_map_pa || ucd + 32 > hc_uefi_map_pa + hc_uefi_map_size) {
           return "UEFI's command descriptor is not where it was";
   }
   ```

   The check compares the UCD address **inside UEFI's transfer list** with the page the
   kernel mapped. On this phone UEFI's list is at `0x48447400` and the UCD it points at is
   somewhere else, so the check fails.

   **Patch 7 in the patcher is exactly this.** Its comment: *"_hc_uefi_slot0: the prebuilt
   asks the loader for the slot it read the UEFI from; this phone has none, so the lookup
   returns nothing instead of dereferencing it."* The byte patch replaces the call with
   `mov x0, #0` (`000080d2`), i.e. **the function returns NULL instead of refusing**.

   The source-level equivalent is to make `_hc_uefi_slot0()` return `NULL` (meaning "no
   objection") rather than the refusal string, so the native driver proceeds.

   Also note the earlier refusal in the *first* source-built run, before the address fix:

   ```
   ufs: the loader offers no area for a list (or not one as expected: controller 11270000,
        area 80210000 of 69632, command descriptors at 4096 of 2048)
   ```

   That check is at `hakios.ufshc.c:1172` and compares the loader's published page against
   the kernel's own constants (`UFSHC_PHYS`, `SLOTS`=32, `ucd_offset`, `ucd_size`,
   `area_size`). It passed after the address fix. The remaining refusal is the one above.

3. With the native driver refused, storage falls back to `hakios.ufs.c`'s request path, and
   **our loader does not serve it**: the loader has no service loop for the shared page
   (`grep -c 'ask.request' mtkloader/mtkloader.c` → 0; there is no `ufs_page->ask` in the
   loader at all). The kernel waits 20 s for an answer that cannot come, then gives up.

**So: patch 7 at source level is the next thing to do, and it is likely the whole of the
storage problem.** The reference tree's loader (`refs/hakios-xnu-kernel/xnuloader/loader.c`)
has the block-read service; ours does not.

## After patch 7, and after the loader fallback: the storage reads now

Done, same day. `_hc_uefi_slot0()` in `/mnt/mainline/xnu-src/xnu-8796.121.2/bsd/dev/hakios.ufshc.c`
now returns NULL, exactly as the prebuilt's byte patch did (`mov x0, #0`). Record in
`docs/kernel-source-patches/hc-uefi-slot0.patch.md`. The kernel was rebuilt and run 120 s
(`~/.hermes/cache/scratch/p7.log`):

```
ufs: native: UEFI's slot 0: e1a00e00 00000000 00000000 0003ffff e1a40e00 00000000 00000000 0003ffff
ufs: native: usable: a list of 32 slots at 80210000 (the loader's), reads in 31 of them, 256 KB each
ufs: no answer from the loader to request 1 in 20 s: the storage is off from now on
ufs: native: unit2: no GPT header to know it by (block size 4096)
ufs: this kernel's own UFS driver is not used: through the loader
[FAIL] mount the iOS volume read only
```

The refusal is gone; `usable` is the line the old prebuilt printed. The blocker moved one
function along, and it is the one this section predicted:

`ufs_native_map()` (`bsd/dev/hakios.ufs.c:1326`) reads block 1 (the GPT header, "EFI PART") of
every unit the loader lists **through the loader** first (`ufs_read_mailbox`), and only then
puts this kernel's list in and reads block 1 of each LUN natively to see which LUN the unit is
on. Our loader never answers a read: `mtkloader.c` publishes the page
(`ufs_setup_shared()` at line 682) but has no loop that looks at `ask.request` and writes
`answer.answered` — `grep -c 'ask.request' mtkloader/mtkloader.c` is 0. The kernel waits
`UFS_TIMEOUT_MS` (20 s), gives up, and `ufs_request()` sets `ufs_dead`, which makes
`ufs_native_in()` fail immediately afterwards (`ufs_dead ? EIO : ufshc_switch_in()`, line 542).

The reference loader does have the service — `block_poll()` in
`refs/hakios-xnu-kernel/xnuloader/loader.c:2128`, called from core 0's watch loop while the
kernel runs — but it serves reads through **UEFI's own Block I/O**, and UEFI is not here. Our
loader cannot read the UFS either: `jump_to_kernel()` (`mtkloader/mtkloader.c:3201`,
`start.S:67`) ends in `eret` into XNU at EL1 and never returns to C, so core 0 is gone, and
the controller is exactly what XNU owns by then.

**The fix, then, is what this section already guessed at, and it works.** `ufs_native_map()` now
tolerates a silent loader:

* `ufs_dead` is cleared before the switch-in, so the 20 s wait cannot poison the native path;
* if the loader gives no copy of block 1, the LUNs themselves become the search: block 1 of
  each one in `UFS_LUN_MASK` is read natively and a LUN whose header parses as a GPT header
  (signature, sane `entries_lba`/table sizes, and the header's own CRC32 over its bytes) is
  taken to be one the phone has;
* a unit is then on the LUN of its own number — which is what the working prebuilt assumed
  (its final loop stores `e->unit` into `unit_lun[e->unit]` with nothing read) — with the
  extra check here that that LUN was really read and really holds a header.

The proof it is right is in the run, not in the reasoning. From
`~/.hermes/cache/scratch/next.log`, 120 s, `cpus=4 touchscreen=1 touch_lat=1 gl=1`:

```
ufs: no answer from the loader to request 1 in 20 s: the storage is off from now on
ufs: native: unit2: no GPT header to know it by, from the loader: the LUNs are read here instead
ufs: native: transfer list switched from UEFI's 00000000:48447400 to this kernel's 00000000:80210000
ufs: native: proof: TEST UNIT READY in this list's slot 0 came back here (OCS 0, response 00, status 00)
ufs: native: LUN 2 holds a GPT header of its own: it is read here
ufs: the partitions (on 3 logical unit(s) of the phone's) are read by this kernel's own UFS driver, its list in the controller
apfs: volume 0 "System" of container 0 (at 0 MB): 45044 files, 16547 directories, 601698 blocks of 4096 used
[ ok ] mount the iOS volume read only
ufs: native: at the end: 37259 reads, 0 errors, 971898880 bytes, 5762 ms waiting (summed over reads), at most 7 in flight
```

**37,259 reads, 0 errors, 927 MB read through this kernel's own driver.** No 20 s hang in the

Two things to note for whoever picks this up:

* **The `[FAIL]` lines that remain are the small root's, not the storage's**: `a synthetic
  /redwood on it`, `the first boot's applications in /Applications`, `the OS cryptex: in
  neither md0 nor the flash`, `the App cryptex`. Those are the ramdisk image's contents, and
  they were failing in the working prebuilt run too.
* **The 20 s wait is worth removing** — it is now pure loss. Either the loader's page should
  say "I cannot serve reads" up front, or `ufs_native_map` should try the native LUN search
  first and use the loader only as a cross-check when it does answer.

Also worth knowing, because it is the same shape as this fix: the **prebuilt's `ufs_native_map`
never compared against the loader at all in its final loop**. Disassembled from
`refs/hakios-xnu-kernel/prebuilt/hakios-kernel` (`_ufs_native_map` at
`0xfffffff0074aa4ac`–`0xfffffff0074aa8d8`): it does ask the loader for block 1 first (the call
at `0xfffffff0074aa60c` is the read, `0xfffffff0074aba10` the function behind it), but when it
builds `unit_lun` in the loop at `0xfffffff0074aa828` it stores `e->unit` straight in with
nothing read. The `mask` is likewise built from the units' own numbers (`1u << e->unit`), which
is why the reference port's `hakios.ufs.c` and ours agree there.

**The difference that mattered was the source tree's `ufs_native_map`, not the prebuilt's.** The
upstream `refs/hakios-xnu-kernel/drivers/storage/hakios.ufs.c` is the reference port's version;
diffing it against ours shows our tree *added* the strict LUN search (comparing each LUN's
block 1 against the loader's copy, and refusing when no LUN matches) and *replaced* the
prebuilt's "the unit's own number is the LUN" assumption with `unit_lun[]` bookkeeping. On a
loader that answers, both work. On a loader that does not, only the prebuilt's shape does.


## The touch driver: it runs, but every report is the same

Good news first — the driver is in the kernel and it talks to the panel:

```
ft3681: chip id 5662, firmware 44
ft3681: ready; a report is read every 5000 us
ft3681: the DMA buffer is at fffffff824d1f000 (physical c4f3a000)
ft3681: report 1: type 0 count 1: 44 01 8d 00 01 00 8c 01 01 02 00 04 00 00
ft3681: report 2: type 0 count 1: 44 01 8d 00 01 00 8c 01 01 02 00 04 00 00
ft3681: report 3: type 0 count 1: 44 01 8d 00 01 00 8c 01 01 02 00 04 00 00
...
ft3681: 58800 reads, 58800 reports (0 idle), 58800 points, 0 failed
```

The chip answers (chip id `5662`, firmware `44` — the right values), 58,800 reads with
**0 failures**, and 58,800 reports. But every report is byte-identical. Decoded, that
report says: header `44 01` → type 0, count 1; point bytes `8d 00 01 00 8c 01` →
event = `(0x8d>>6)&3` = 2, id = `(0x01>>4)&0xf` = 0, x = `((0x8d&0x0f)<<12)|(0x00<<4)|(0x8c>>4)`
= 0xd000|0x08 = 53256, y = `((0x01&0x0f)<<12)|(0x00<<4)|(0x8c&0x0f)` = 0x100c = 4108.

x = 53256 is past `PANEL_X_MAX` (17279), so `scale_x()` returns 65535 — which is exactly
what the one posted sample was:

```
tl: p 1 0 65535 7011 at 25522425
```

One sample in 58,800 reads, because the coordinates never change, so the driver posts the
press once and never a move.

Compare the loader's own probe in the same log:

```
touch: register 0x0x1: 0xff 0xff 0xff 0xff 0xff 0xff 0xff 0xff (all 0xff)
touch: 62-byte read of the chip id register: 0x56 0x1 0x0 0x44 (the long read works)
touch: no point in 1000 report frames (the panel said 0xff every time)
```

The loader's read of register 0x01 gives **all 0xff** — the panel had nothing to say at
that moment. The kernel's read of the same register gives `44 01 8d 00 ...`. So the two are
reading **different data**, and the kernel's is stale-looking: `0x44` is the firmware
version, `0x8d` is the vendor id — both values the *loader* read earlier in the same boot
(`touch: probe chip_id=0x5662 fw_ver=0x44 vendor=0x8d points=15`). The kernel's report
looks like the panel's **chip-information block**, not a touch frame.

Everything in the two I²C paths was compared line by line and matches: the register
offsets, the timings (`TIMING 0x0419`, `LTIMING 0x0123`, `EXT_CONF 0x5801`,
`SDA_TIMING 0x100a`), `i2c0_prepare()` (the kernel's always sets `DMA_EN|DMAACK_EN|ASYNC_MODE`,
the loader's sets them only for DMA — same effect), `i2c0_init_hw()` (identical register
sequence), the DMA engine's `APDMA_REG_*` programming (identical), the slave address
`0x38 << 1`.

The differences that remain, in order of suspicion:

1. **Cache handling around the RX buffer.** The loader does
   `dcache_clean_range(rx_buf, 64)` — clean only — and its buffers are 64-byte-aligned
   static arrays (`mtkloader/mtki2c.h:124-125`). The kernel does
   `FlushPoC_DcacheRegion(rx_buffer, 256)` — **clean *and* invalidate** — before and after,
   on `dma_buffer + 256` inside a page. `FlushPoC_DcacheRegion` is `dc civac`
   (`osfmk/arm64/caches_asm.s:396`), i.e. it invalidates. The kernel's RX buffer is at
   `+256` in a page it also uses for TX at `+0`, and the transfer is 62 bytes at
   `+256`, so the flush of 256 bytes covers it — but the *invalidate* before the transfer
   may discard the panel's data if the engine writes to the buffer before the flush lands.
   Note the kernel's own UFS driver uses `FlushPoC_DcacheRegion` on its slot buffers and
   that works, so this is not obviously wrong — it is just the one remaining difference
   from a path that is *proven* to read real coordinates.
2. **The RX buffer's address.** The loader passes the **virtual** address of a static
   array (the loader runs with the MMU off, so virtual == physical). The kernel passes
   `dma_buffer_pa` from `kvtophys()`, with the TX and RX at `pa` and `pa+256`. The
   `APDMA_REG_TX_4G_MODE`/`RX_4G_MODE` get `pa >> 32` = 0 in both cases. The kernel's
   `dma_buffer_pa` is `0xc4f3a000` — inside the DRAM window (base `0x40000000`), so it is
   reachable. Not obviously wrong either.
3. **The chip is never reset and its rail is never powered by the kernel.** The loader's
   sequence is: hold the chip in reset → power the touch rail (MT6360 LDO2 on I2C5) →
   release reset → then read. The kernel's driver **does none of this**; its own header
   comment says the loader does it before the kernel starts. In this run the loader did do
   it (the log shows `mt6360: enable write ok, reg=0xc4`), so the chip was up — but the
   panel may have been left in a state where register 0x01 does not return frames, or the
   loader's own 62-byte reads left it mid-transfer.

**The cheapest next experiment** (one run, 120 s): make the kernel's driver do the
loader's full bring-up itself — assert reset, enable the rail, release reset, 20 ms delay —
before reading, exactly as `mtkloader/mtkloader.c:2566-2574` does. The functions exist in
`mtkloader/mt6360.h` (`mt6360_enable_touch_rail`) and `mtki2c.h` (`fts_reset_assert`,
`fts_reset_release`); they will have to be ported into the kernel driver.

**The other cheap experiment**: change the cache handling of the RX buffer to match the
loader exactly (clean only, not invalidate), and make the TX and RX buffers two separate
page-aligned buffers rather than one page split at `+256`.

And a third: print the report read at a *register the loader also read* (the chip id
register, `0xa3`) through the kernel's own path. If the kernel's 62-byte read of `0xa3`
returns `0x56 0x01 0x00 0x44` — the loader's answer — then the transfer is fine and the
problem is the panel's state; if it returns the same stale block, the transfer path is
wrong.

`/mnt/mainline/xnu-src/xnu-8796.121.2/bsd/dev/` and into
`refs/hakios-xnu-kernel/drivers/<subsystem>/`. Do both, then rebuild.

## Commands

```bash
cd /mnt/project/Misc/hakios/hakios-x6739

# build (exits 2 on the kext symbol-set steps; the kernel is built anyway)
bash tools/build-kernel-linux.sh -j8

# copy the built kernel in
cp /mnt/mainline/xnu-src/xnu-8796.121.2/BUILD/obj/DEVELOPMENT_ARM64_BCM2837/mach.development.bcm2837 \
   mach.development.mt6893

# run, 120 s
export HAKIOS_SERIAL=102562537K104189
HAKIOS_QUIET_JOBS=1 XNU_ARGS="cpus=4 touchscreen=1 touch_lat=1 gl=1" \
  XNU_SECS=120 XNU_LOG_OUT=~/.hermes/cache/scratch/next.log \
  bash tools/xnu-cycle.sh

# the log
adb shell su -c 'cat /sys/fs/pstore/console-ramoops-0'
```

`touch_lat=1` makes the kernel log every sample it posts (`tl: p ...`), which is how the
touch path is judged.

## Rules that hold

* One root shell command per `adb` invocation — never `&&` or `;` inside a single quoted
  `su -c` string; it silently drops root for everything after the first command.
* Never work in `/tmp` (RAM-backed tmpfs here). Scratch is `~/.hermes/cache/scratch`.
* Do not commit to `refs/hakios-xnu-kernel` — it is upstream and read-only for device work.
  Copying a file *into* it so the build sees it is fine; committing is not.
* The phone leaves USB entirely for 2–4 min during an init-retry loop; poll for ~10 min
  before calling it dead. A dark screen after that needs a power cycle and a USB reseat.
* Nothing is "working" until it has been seen on the panel or in a log. `device.conf` says
  `missing` for every area.
